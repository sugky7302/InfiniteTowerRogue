# RxWC3 M3 實作計畫

本計畫以 `../PLAN.md` 與本次任務為準。只實作 WC3 事件來源與驗證範例。不修改既有 operator、Signal 或排程器。

## 設計

1. `EventNatives` 隔開原生註冊、快照讀取與傷害修改。`createWc3Events(natives)` 建立可測試的事件來源。正式實作以模組內 `declare` 宣告原生函式。載入入口時不呼叫原生函式。
2. 資料使用原生 handle。結構型別只保留原生 handle 的型別識別欄位，不載入 WC3 全域型別或 w3ts。這避免每次事件建立包裝物件。單位篩選接受原生單位及 `{ handle: UnitHandle }`，因此可傳入 w3ts `Unit`。
3. `fromTrigger(register, read, natives?)` 每次訂閱建立獨立觸發器。取消訂閱時銷毀。註冊失敗時也銷毀。同步性由註冊事件決定；M3 只供同步事件使用，不加入 M4 執行時標記。
4. 每種玩家單位事件各有一個延遲建立的觸發器。建立後保留。中樞使用依單位索引的 `Map<UnitHandle, Subject>`。最後一個訂閱取消時刪除 Map 項目。死亡不結束串流。
5. 傷害 API 為全域 `onDamaging`、`onDamaged`，以及 `.ofTarget(unit)`、`.ofSource(unit)`。施法與死亡使用 `.of(unit)`。中樞依訂閱順序合併全域及相關單位的訂閱。每次事件只查詢相關 Map 項目，不複製訂閱陣列。取消時先關閉訂閱，分發結束後整理。
6. 資料在原生回呼內複製為一般物件。唯讀傷害資料沒有修改方法。可修改傷害提供 `setAmount`、`setAttackType`、`setDamageType`、`setWeaponType`。成功修改後更新同一份快照，後續訂閱者讀到新值。方法使用原型，不為每個方法建立閉包。
7. 修改只限目前分發中的傷害。分發結束或巢狀事件暫時取得事件環境時，舊傷害修改被拒絕，並由 `reportUnhandledError` 回報。使用 `finally` 恢復外層環境。每個觸發器回呼使用 `try/catch`。沿用既有訂閱者錯誤隔離。
8. 訂閱順序使用有界整數。達到 2147483000 時，在非分發期間新增訂閱前重新編號目前訂閱。若正處於分發，拒絕該次新增並回報錯誤。這避免巢狀分發中的順序改變。此限制不增加每次事件的掃描成本。
9. 聊天共用一個延遲建立的觸發器，註冊全部玩家及空字串比對。資料為玩家與完整訊息。聊天、傷害、施法與死亡均判定為同步事件；來源註解列出依據。不得在本地分支建立或訂閱這些來源。

## 驗證計畫

- Node 假原生介面：延遲建立、單一觸發器、單位分發、Map 清理、延遲快照、傷害修改順序、有效期、巢狀事件、錯誤隔離、聊天與取消。
- 型別檢查：唯讀傷害沒有修改方法；篩選接受原生 handle 與 w3ts 形狀。
- 假時鐘：`onSpellChannel.of(caster)` 配合 `switchMap`、`timer(0.8, { phase: Phase.Combat })` 與 `takeUntil(onSpellEndCast.of(caster))`。中斷不送值，持續超過 0.8 秒送值。檢查任務及訂閱清理。
- 執行 `npm run test:unit`、`npm run build`、獨立 TSTL 與 Lua 5.3 假原生驗證。掃描建置 Lua 的禁止常數。

## 遊戲內待確認項目

以 `m3-example.ts` 取代 M2 hook，保留 M2 檔案及 `main.ts` 其他內容。使用者執行 `npm run test` 後確認：

1. 兩個敵對單位互相攻擊。傷害前輸出原值及半值。後續訂閱讀到半值。傷害後輸出最終值；護甲可能使它不同於半值。
2. 單位死亡時輸出死亡單位與兇手。
3. 大法師在第 2 秒收到暴風雪命令，命令成功應為 `true`。五個階段依序輸出「引導、施放、生效、完成、結束」。第一次引導持續超過 0.8 秒時，另輸出「M3 施法 1：0.8 秒計時送出值。」。這個值表示計時到期，不代表技能已完成。
4. 第 12 秒重設暴風雪冷卻，再次下達施法命令，命令成功應為 `true`。第二次引導後 0.2 秒下達停止命令。應輸出「M3 施法 2：結束」，不應輸出第二次的 0.8 秒計時值或技能完成。第二次可能在施放或生效之前中斷。實際原生階段順序仍須在遊戲中確認。
5. 輸入任意聊天訊息、`-save`、`-load 測試`、`-lang zh-TW`。輸出正確的玩家編號與完整訊息。

遊戲內驗證尚待使用者執行。Node 與 Lua 假原生測試不能取代 WC3 驗證。完成狀態保持 `false`。

## 與主設計稿的差異

- 依本次任務使用 TypeScript `try/catch`，不直接使用 `xpcall`。
- 傷害篩選明確分為 `.ofTarget` 與 `.ofSource`。施法與死亡保留 `.of`。
- 依單位的 Subject 使用 M3 專用子類別，合併相關訂閱的順序。不修改既有 Subject 行為。
- 可修改傷害使用含原型方法的快照物件。唯讀傷害與其他事件使用物件字面值。這避免每次傷害為四個修改方法建立閉包。
- 遊戲範例使用暴風雪。它有足夠長的引導時間，可同時驗證 0.8 秒計時與停止命令。瞬發技能不適合此取消案例。
