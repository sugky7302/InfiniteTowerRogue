# 存檔系統（首版：基礎架構）

## 目的

- 玩家輸入 `-save`，保存局外資料；輸入 `-load`，讀回資料。
- 首版只建立存檔的基礎架構，以範例資料驗證完整流程。日後由各遊戲系統（角色、倉庫、玩家紀錄等）登錄自己的資料。

## 已決策（2026-11-03）

| 問題 | 決策 |
|---|---|
| 讀檔方式 | 兩者都支援：`-load` 自動讀取本機存檔檔案並同步；`-load <存檔碼>` 手動輸入（換電腦時使用）。 |
| 保存內容 | 首版只做基礎架構與範例資料。 |
| 活動中途保存（「暫停並退出」） | 首版不做。活動系統存在後再設計。 |
| 防竄改 | 首版就做（使用者於 2026-11-03 更改決定）。見「設計 3a」。 |
| 多人 | 架構支援每名玩家各自存檔與讀檔；首版以單人驗證。 |
| 參考 | 世界 RPG、西部荒野、卡利隆王國的存檔碼做法。 |

## 用語

| 用語 | 意思 |
|---|---|
| 存檔資料 | 遊戲要保存的值（例如等級、金錢、物品）。 |
| 資料格式 | 存檔資料的欄位、型別、範圍與版本。 |
| 存檔碼 | 存檔資料經打包、檢查碼、編碼後的字串。玩家可以抄寫。 |
| 存檔檔案 | 寫入 `CustomMapData` 的檔案，含存檔碼。 |

## 範圍

### 包含

1. 資料格式：欄位定義、版本號、舊版本轉換。
2. 編碼：位元打包 → 檢查碼 → 字元編碼 → 分組。
3. `-save`：產生存檔碼，寫入存檔檔案，並顯示給玩家。
4. `-load`：讀取本機存檔檔案，分段同步給全部玩家，解碼後套用。
5. `-load <存檔碼>`：從聊天訊息讀取存檔碼（聊天事件已同步），解碼後套用。存檔碼較長時，支援分段輸入。
6. RxWC3 的 `sync` 支援分段傳送（新增功能）。
7. 範例資料與範例地圖。

### 不包含

- 活動中途保存、多個存檔欄位（首版只有一個）。
- 真正的遊戲系統資料（日後由各系統登錄）。

## 設計

### 1. 模組位置

| 位置 | 內容 |
|---|---|
| `src/feature/save/` | 資料格式、編碼、存檔與讀檔流程（純邏輯，可在 Node 測試） |
| `src/shared/rxwc3/sync/` | 分段同步（通用功能） |
| `src/shared/file-io/` | 既有的檔案讀寫模組 |
| `src/shared/wc3-def/` | 需要的原生函式介面與 WC3 實作 |

### 2. 資料格式

- 每個欄位記錄：名稱、型別（無號整數、布林、固定長度清單等）、範圍（決定位元數）。
- 存檔碼開頭保存格式版本號。讀到舊版本時，依序執行轉換函式，轉成目前版本。
- 物品等 WC3 物件以**目錄索引**保存，不保存 32 位元的物件代碼，以縮短存檔碼。
- 日後的系統以「登錄區段」的方式加入欄位，不直接修改其他系統的欄位。

### 3. 編碼流程

```
存檔資料 → 依資料格式位元打包 → 加入驗證碼 → 混淆 → 字元編碼 → 分組（例如每 5 字元一組，以 - 分隔）
```

- 字元集：避免容易混淆的字元（例如 Crockford Base32：不含 `I`、`L`、`O`、`U`）。解碼時不分大小寫，並把 `O` 視為 `0`、`I`／`L` 視為 `1`。
- 驗證碼：同時用於發現錯字與防竄改（見「3a」）。
- 32 位元限制：WC3 Lua 為 32 位元整數。位元運算的中間值不得超過整數上限；Node 測試須檢查（見 `AGENTS.md`）。
- 字元集必須是 file-io 允許的字元（見 `.github/skills/i18n/SKILL.md` 的 file-io 一節）。

### 3a. 防竄改

| 措施 | 內容 | 防止 |
|---|---|---|
| 帶密鑰的驗證碼 | 以地圖內的密鑰與存檔資料計算雜湊，放入存檔碼。讀檔時重新計算並比對 | 修改存檔碼的任一字元 |
| 混淆 | 以密鑰產生的序列打亂位元，使相同欄位在存檔碼中的位置與字元不固定 | 從多個存檔碼比對出欄位位置 |
| 綁定玩家名稱 | 驗證碼的計算包含玩家名稱（使用者於 2026-11-03 決定綁定） | 把存檔碼給其他玩家使用 |

- 雜湊與混淆只使用 32 位元整數運算（見 `AGENTS.md`）。
- 玩家名稱：Reforged 的 `GetPlayerName` 是否包含 `#1234` 這類數字標籤，須在遊戲中確認。計算前先正規化（例如統一大小寫、去除前後空白），並記錄實際格式。玩家更改 Battle.net 名稱後，舊存檔碼無法使用（已知限制）。
- 驗證失敗時，只顯示「存檔碼無效」，不說明是錯字、竄改或玩家不符，以免提供線索。
- 密鑰集中在一個模組。日後更換密鑰時，以版本號區分新舊存檔碼。

### 4. `-save`

1. 從各系統收集存檔資料（首版為範例資料），產生存檔碼。
2. 寫入存檔檔案（file-io，本地）。
3. 另寫一份方便閱讀的檔案，內含可直接輸入的 `-load` 指令，供玩家抄寫或換電腦使用。
4. 在畫面上只對該玩家顯示結果與存檔碼。

- 存檔資料的收集是同步運算；寫檔只在該玩家的用戶端執行（本地）。
- file-io 只能回報「已送出」。畫面上說明這一點。

### 5. `-load`（自動讀檔）

1. 該玩家的用戶端讀取本機存檔檔案（本地）。
2. 以分段同步送出存檔碼，全部用戶端收到相同資料。
3. 全部用戶端解碼並驗證（版本、檢查碼）。
4. 成功時套用資料（同步）；失敗時只對該玩家顯示原因。

- 檔案不存在或損壞時，提示玩家改用 `-load <存檔碼>`。

### 6. `-load <存檔碼>`（手動輸入）

- 聊天事件已同步，可直接解碼，不需要 `sync`。
- WC3 聊天輸入有字數上限（約 127 字元，須在遊戲中確認）。存檔碼超過上限時分段輸入，例如 `-load 1/3 <片段>`、`-load 2/3 <片段>`、`-load 3/3 <片段>`。全部片段到齊後才解碼。
- 存檔檔案中的可閱讀版本，直接列出這些分段指令。

### 7. 分段同步（RxWC3）

- `sync` 目前單次上限 240 位元組，不分段（`docs/rxwc3/m4/PLAN.md`）。
- 新增分段傳送：送出端切成多段並加上序號；接收端依序重組，全部到齊後才送出一個值。
- 須處理：片段遺失或逾時、同一玩家重複送出、片段順序。
- 這是 RxWC3 的新增功能，不得改變既有 `sync` 的行為。

### 8. 範例資料（試玩）

| 欄位 | 範圍 | 說明 |
|---|---|---|
| 英雄等級 | 1～100 | — |
| 金錢 | 0～1,000,000 | — |
| 物品 | 最多 6 個，每個為目錄索引（0 表示空） | 目錄為範例中的少量物品 |

範例地圖提供指令修改範例資料（例如 `-save-demo gold 500`）並顯示目前值，以驗證存檔與讀檔前後一致。

## 已知限制

- 防竄改只能防止一般玩家修改。地圖檔可以被解開，密鑰可能被找到。
- 存檔檔案只存在本機。換電腦時須手動輸入存檔碼。
- file-io 無法確認檔案是否真的寫入成功。
- 離線單人時，`GetPlayerName` 傳回用戶端語言的文字（正體中文為 `本地玩家`，2026-11-03 確認）。在某一語言用戶端產生的存檔碼，可能無法在另一語言的用戶端離線使用。

## 待遊戲內驗證

1. WC3 聊天輸入的實際字數上限。
1a. `GetPlayerName` 的實際格式；另一名玩家（或改名後）使用同一存檔碼時被拒絕。
2. 分段同步在遊戲中正確重組。
3. 存檔檔案的位置與內容可以閱讀、可以抄寫。
4. 存檔後關閉地圖，重新開啟後 `-load` 讀回相同資料。
