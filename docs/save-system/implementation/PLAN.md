# V1 至 V3 實作記錄

唯一規格為 `../PLAN.md`。本記錄的完成狀態只表示 V1 至 V3 的實作與工具驗證完成。主規格的完成狀態仍為 false。V4 由使用者在遊戲中執行。

## V1 資料格式

- `SaveRegistry.register` 登錄一個版本及其區段。系統提供 `SaveSection`，由格式登錄清單決定順序。欄位包含名稱、種類、範圍與清單長度。
- 支援無號整數、布林與固定長度整數清單。整數範圍為 0 至 16777215。每個格式最多打包 512 位元組，包含開頭的版本位元組。
- 每個版本保存獨立的區段清單。新增欄位時登錄新版本，並在前一版本提供 `migrate`。解碼依序轉換，每一步都檢查下一版格式。
- 編碼器建立時複製登錄資料。之後修改來源設定或登錄其他版本，都不會改變既有編碼器。
- 範例目前使用格式第 2 版。英雄等級 1 至 100 使用 7 位元，金錢 0 至 1000000 使用 20 位元，六個物品目錄索引各使用 2 位元。0 表示空格。索引 1、2、3 分別對應 `ratf`、`rst1`、`rde1`。
- 第 1 版供相容轉換測試使用。金錢上限為 65535，物品為三格。轉為第 2 版時保留原值，並在末尾加入三個空格。階段 V1、V2、V3 與資料格式版本是不同的編號。

## V1 編碼與驗證

1. 依登錄順序逐位元打包。最後一個位元組以零填充。解碼拒絕多餘位元組、非零填充與欄位越界。
2. 計算 HMAC-SHA-256。輸入包含用途標記、密鑰版本、玩家名稱的 UTF-8 長度、正規化名稱及打包資料。取前 16 位元組作為驗證碼。
3. 以驗證碼及密鑰產生 HMAC 序列。`order` 用途產生 Fisher-Yates 位元組排列，`mask` 用途產生 XOR 遮罩。不同資料有不同排列與遮罩。
4. 封裝為資料版本、密鑰版本、16 位元組驗證碼及混淆資料。解碼還會比對公開資料版本與打包版本。
5. 輸出 Crockford Base32，每五個字元以連字號分組。解碼接受大小寫、O、I、L 別名，並忽略 ASCII 空白與連字號。拒絕不合法字元及非標準末尾填充。

密鑰集中於 `keys.ts`。密鑰版本目前為 1。更換時須增加版本，並保留舊密鑰以讀取舊碼。驗證、版本或轉換失敗都只回傳 undefined。聊天統一顯示「存檔碼無效」，不揭露驗證失敗的原因。

名稱會去除前後 ASCII 空白，並將 a 至 z 轉為 A 至 Z。其他 UTF-8 位元組保留。名稱長度以正規化後的 UTF-8 計算，上限為 256 位元組。Node 與 Lua 使用相同的位元組資料，含中文及非 BMP 字元。

### 32 位元處理

| 運算 | 上限與處理 |
|---|---|
| SHA-256 字 | 使用兩個 16 位元整數，完全不建立無號 32 位元字 |
| SHA 加法 | 最多五個肢相加，低肢和最多 327675，高肢含進位最多 327679，再對 65536 取餘數 |
| SHA 旋轉與位移 | 先遮罩再左移，每個結果最多 65535；補數用 XOR 65535 |
| 欄位打包 | 每次只累積一個位元組，最多 255；欄位值最多 16777215，除數最多 8388608 |
| 欄位解包 | 先檢查差值範圍，再加最小值，避免無效資料產生過大的中間值 |
| Base32 | 輸出後立即移除已消耗位元，累積器最多 4095 |
| 排列抽樣 | 兩個位元組組成樣本，最多 65535 |
| UTF-8 | 碼點與代理對中間值小於 2097152 |
| 傳輸序號 | 最多 1048575；到達上限即拒絕增加，不回繞 |
| 片段數字解析 | 最多七位十進位數，中間值最多 9999999 |

以上存檔算術都小於 16777216，符合 int32，且可由 float32 精確表示。時間使用既有 Clock 的整數毫秒，不累加浮點秒數。Node 測試將稽核回呼接到實際雜湊加法、打包、解包、排列抽樣及 Base32 累積器，檢查整數上限及 `Math.fround(value) === value`。測試另檢查旋轉位移的最大值及 24 位元欄位邊界。SHA 與 HMAC 以九組不同長度的輸入比對 Node 標準實作。

錯字測試遍歷一份存檔碼的每個有效位置，替換成其他 31 個 Base32 字元，全部無效。大小寫、別名、分組與空白依規格視為相同輸入。

## V2 分段同步

- 新增 `syncChunked`，從 RxWC3 的 `index.ts` 匯出。它使用既有 `sync` 傳送每個字串封包。
- 既有 `sync.ts` 及其限制未修改。分段 API 沿用相同的 prefix 登錄表。因此，prefix 也不能與一般 sync 重複。
- 封包格式為 `傳輸序號/片段索引/總片數:資料`。索引從 1 開始。預設每片 200 個 UTF-8 位元組，連同標頭低於 240 位元組。
- `chunkBytes` 可設為 4 至 200。每次資料最多 4096 位元組、64 片。送出前先檢查全部資料，超限時不送出任何片段。
- 只有擁有者執行編碼與送出。訂閱及取消都必須在共同流程執行。來源完成或編碼失敗不會關閉接收器。
- 接收端以索引保存片段，允許亂序及相同片段重複到達。只有全部到齊才依序串接並解碼一次。
- 收到較新序號時，清除舊資料及逾時任務。完成、衝突或逾時的序號不可重播，較舊序號一律忽略。
- 從第一片開始計時，預設 15000 毫秒。片段缺少時不輸出部分值，到期清理並呼叫失敗通知。取消訂閱也移除任務。
- 逾時排程在同步接收事件中建立。它使用共同流程已安裝的 uiClock，避免在本地建立原生計時器。

## V3 範例與本地檔案

- `installSaveChat` 接收聊天 Observable、玩家清單、file-io、原生函式介面、SyncNatives、Clock 及編碼器。Node 測試使用兩個假的用戶端及獨立檔案。
- 範例資料保存在每名玩家各自的 Map。指令修改的是此範例資料。`-save-demo show` 顯示等級、金錢、六格索引及未修改的玩家名稱。
- `-save` 在共同流程收集並編碼。只有擁有者的本地訂閱寫檔及顯示結果。
- 存檔路徑為 `CustomMapData\InfiniteTowerRogue\save.pld`。可閱讀檔案為同目錄的 `save-commands.pld`。
- 新增 file-io 的 `writeReadable`。每條受限 ASCII 文字寫成一個完整的 `// -load ...` 註解行。玩家複製 `// ` 後面的指令即可，不必合併固定長度的 JASS 字串片段。這份檔案供玩家閱讀，資料讀回仍使用 save.pld。
- `writeReadable` 沿用路徑檢查、4096 個 ASCII 字元限制與「已送出」狀態。每行上限為 126，不接受引號、反斜線或換行輸入。寫入失敗仍清理緩衝。
- `-load` 只由擁有者本地讀檔。讀取結果包含同步請求序號，再經分段同步送達全部用戶端。各用戶端驗證後才同步套用。
- 每個自動讀檔請求有 15000 毫秒期限。即使全部封包遺失或送出被拒絕，也會顯示逾時。遲到結果、較舊請求及被手動輸入取代的自動結果均不套用。
- 檔案不存在、框架損壞、資料錯誤或讀取例外，都提示改用 `-load <存檔碼>`。寫檔結果同時說明 file-io 只能回報已送出，無法確認磁碟成功。
- 範例明確使用 `chunkBytes: 20`，讓目前約 46 字元的短碼也經多個封包傳送。V4 可直接測試自動多段重組。
- 手動聊天已同步，直接收集與驗證，不再送出 sync 封包。每片最多 80 個有效 ASCII 字元。分段指令最長 92 字元，為約 127 字元的聊天上限保留至少 35 字元。
- 手動片段等待 60000 毫秒。第一次的 1/n 可以晚到。已收到 1/n 後再次輸入 1/n，視為新一批。失敗後須重新輸入全部片段。最終內容仍須通過完整驗證。
- `-load 1/1 <片段>` 也支援。目前短碼的指令檔同時列出完整輸入與此分段格式。
- `SaveNatives` 只包裝玩家名稱及文字顯示。正式原生實作載入時不呼叫原生函式。
- 範例模組在 compiletime 呼叫既有 `scripts/file-io.cjs` 預留 A0IO，再由 main 原有的 objectData.save 儲存。file-io 的 prepare 在共同流程預載技能。
- main 僅替換範例 import 與 hook。技能範例檔案保留。

## 實作補充與差異

1. 規格未指定雜湊、碼長及逾時數值。本次選擇 128 位元截短 HMAC、512 位元組打包上限、1100 字元解碼輸入上限、自動 15 秒及手動 60 秒期限。最大產生碼為 1017 字元，含分組。
2. 名稱大小寫統一限於 ASCII。原因是 Lua 的標準大小寫函式以位元組運作，而 Node 使用 Unicode。保留其他位元組可避免兩端得到不同驗證值。重音字母等非 ASCII 字母的大小寫仍有區別。
3. 可閱讀檔案使用完整註解行。既有 write 會把框架切成 96 字元，可能拆開手動指令。因此新增 writeReadable，既有 write 與 read 行為保留。
4. 實作期間工作區加入 FSD 分層規則與 Steiger 套件。此次路徑採用任務明確指定的 src/feature/save。AGENTS.md、Steiger 相依項目與 pnpm-lock.yaml 的其他工作變更保留。
5. 存檔範例替換技能範例後，既有建置流程將 i18n/objects/zh-TW.json 更新為空的物件範本。其他語言的舊翻譯由既有流程保留。
